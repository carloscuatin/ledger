# Ledger — architecture

A wallet ledger for multi-tenant fintechs, built to learn Java and Spring Boot in a domain where
Spring earns its place: money with ACID consistency, resumable batch jobs and OAuth2 security.

## Current status

`ledger-app` boots with Spring Modulith, and the build verifies module boundaries
(`ModularityTest`) and layers (`LayersTest`). Phase 0 (plain Java domain) has started: the `ledger`
module has the `Money` value object (minor units with the currency scale, strict parsing, exact
arithmetic, half-even rates, comparisons and plain decimal rendering) and its unchecked domain
errors.

## Decisions

| # | Decision | Why | Rejected |
|---|---|---|---|
| 1 | Two phases. **Phase 1**: the ledger as a modular monolith + auth-server + BFF + webhooks service, with all security and queue-based events, deployed. **Phase 2**: reconciliation is split into its own service and subscribes its queue to the journal topic | A money system does not exist without its security; domain boundaries are validated inside the monolith before splitting services | Ledger and reconciliation as microservices in phase 1: sagas to move money |
| 2 | Spring Modulith + hexagonal per module | Modulith verifies boundaries in a test and ships an outbox (`event_publication`) that publishes integration events without touching the domain | Classic controller/service/repository layers coupled to JPA |
| 3 | Deployment: ECS Fargate + RDS Postgres | The most common setup in companies running Spring; it does not repeat market-lab's Kubernetes | Kubernetes |
| 4 | One `ledger-app` image, three profiles: `api`, `batch` (scheduled task) and `migrate` (Flyway before each deployment) | They share code and version; the batch costs nothing while it is not running | An always-on batch service; migrating on API startup (instances race) |
| 5 | The ledger is never split | Debit and credit go in one ACID transaction | — |
| 6 | Web console behind a **BFF**: tokens only on the server, HttpOnly/Secure/SameSite=Strict cookie, Spring Session JDBC | An XSS has no token to steal; recommended by the IETF draft *OAuth 2.0 for Browser-Based Apps* | Tokens in localStorage or JS memory |
| 7 | API clients use the **FAPI 2.0** profile: private_key_jwt, PAR, PKCE, **DPoP** | A stolen token is useless without the private key | Bearer tokens with client_secret |
| 8 | **Opaque access token + introspection** in every service that receives tokens (ledger, webhooks and, in phase 2, reconciliation) | Immediate revocation: a blocked account fails on its next request | Self-contained JWT (revocation only at expiry) |
| 9 | MFA with **passkeys** (Spring Security 7.1 WebAuthn) and **step-up** (RFC 9470) above an amount threshold; dual approval for manual adjustments | The only phishing-resistant factor; login MFA does not protect a hijacked session | SMS, TOTP |
| 10 | Defense in the database: the app has no UPDATE/DELETE on journal entries; hash-chained audit log | A bug or an injection cannot rewrite history | Immutability enforced only in code |
| 11 | Platform: WAF + rate limiting, least-privilege IAM task role per service, KMS on RDS and S3, secret rotation, VPC endpoints | Least privilege and defense in depth | — |
| 12 | Java 25 (LTS) + Maven | Current LTS, supported by Spring Boot 4; Maven is the enterprise standard | Gradle, Java 21 |
| 13 | Terraform, one module per provider with the same outputs | Market standard and multi-cloud | AWS CDK |
| 14 | Local: the same Terraform applied against Floci (ECS and RDS start real containers); Testcontainers in tests | What runs locally is what gets deployed | A separate docker compose that drifts from the deployment |
| 15 | **Currency**: starts with COP only, with the model ready for more. `Money` = amount + `Currency` (ISO 4217), and its scale comes from the currency (`getDefaultFractionDigits`), never from a constant. Each account has a fixed currency from creation. A journal entry balances **per currency** (Σ debits = Σ credits in each currency). Each tenant has its list of enabled currencies (today `[COP]`), and `FeeSchedule` is per currency. Cross-currency transfers do not exist yet, but the model allows them: two legs against FX position accounts inside the same entry, which balances per currency | Adding a currency is configuration plus tests, not a model or schema change | Fixed 2-decimal scale (breaks currencies with 0 or 3 decimals); amounts without currency |
| 16 | Portability: the app only knows an OCI image, env vars, PostgreSQL 16+, a storage port, an events port (SNS/SQS on AWS, Pub/Sub on GCP, each in its own externalizer), OTLP and JSON logs. **AWS** is the main deployment; **GCP** is the second real deployment (Cloud Run, Cloud SQL, Cloud Storage with HMAC over the same S3 adapter, Cloud Armor, Cloud KMS); **Azure** stays as a reference in the contract | Two clouds deployed with the same image prove portability; GCP meets the whole contract without lowering any guarantee; the only cloud-specific pieces are the event externalizer and the Terraform module | Railway: no WAF, no customer-managed keys and an unofficial Terraform provider; it would lower the ledger's guarantees. Cloud SDKs inside use cases |
| 17 | **Console**: a React SPA and a BFF, with three role-based areas: **Finance** (operator, approver), **Administration** (internal users, roles, step-up thresholds, chart of accounts) and **Developers** (OAuth2 client registration with RFC 7591, client JWKS, key rotation). The UI hides what the role cannot do; authorization lives in the BFF and the API | A console that grows by area without rework; the developer portal is how a client onboards to a FAPI API | Thymeleaf + htmx (no SPA to protect), Next.js as BFF (less Java), Vaadin (niche), an account-holder area (another product and threat model) |
| 18 | **BFF**: Spring Cloud Gateway Server MVC + `oauth2Login` with a custom DPoP relay filter: it signs one proof per request (`htm`, `htu`, `ath`) with the BFF key stored in Secrets Manager. The token is requested with DPoP through the token client's `setHeadersConverter`. User data comes from the ID token | The gateway's `TokenRelay` only sends `Bearer`, which the ledger rejects for a DPoP-bound token (RFC 9449 §7.2), and Spring Security's `oauth2-client` does not implement DPoP | Standard `TokenRelay`; a BFF without DPoP, which leaves reusable tokens in the session store |
| 19 | **Auth-server**: `oauth2ResourceServer().dPoP()` in its own filter chain, covered by a test that calls `/oauth2/register` with a DPoP token | Since 7.1 the auth-server rejects its own DPoP tokens on `/userinfo` and the client registration endpoints ([spring-security#19876](https://github.com/spring-projects/spring-security/issues/19876)); this is the configuration the issue documents | Bearer tokens for the developer portal |
| 20 | **Maven monorepo**: `ledger-app` (ledger and reconciliation modules), `auth-server`, `console-bff`, `console-web` (React + Vite), `libs/dpop`, `contracts/` (OpenAPI and event schemas), `infra/terraform/{modules,aws,gcp,envs}`, `docs/`. Services share only technical libraries and contracts, never domain classes. Each module is added when its step of the plan arrives | A PR shows a contract change end to end; sharing domain classes would couple bounded contexts and force joint deployments | One repo per service (multiplies CI and contract versioning with no teams to justify it); a shared domain module |
| 21 | **CDN edge**: all traffic enters through CloudFront. `console.*` serves the SPA from S3 (Origin Access Control, private bucket) and routes `/bff/*`, `/oauth2/*` and `/login/*` by path to the ALB, so the browser sees a single origin. `auth.*` and `api.*` go through CloudFront without caching. WAF on CloudFront; the ALB only accepts the CloudFront prefix list plus a secret origin header. CSP and security headers through a response headers policy. CloudFront forwards `Host` and the app uses `forward-headers-strategy=framework`, so the DPoP proof's `htu` matches the public URL. GCP: an Application Load Balancer with a backend bucket + Cloud CDN and Cloud Run by path | Static content is served at the edge without using BFF tasks; the frontend deploys without rebuilding the Java image; a single entry point with WAF; Floci emulates CloudFront with real traffic (S3 and custom origins) | SPA inside the BFF image; CloudFront VPC origins (Floci does not emulate it, breaking local parity) |
| 22 | **Business**: a wallet ledger for fintechs. Capabilities: direct and two-phase transfers (hold → post, void or expire), fees inside the same journal entry, limits and overdraft by account policy, and a daily close with value dates | A concrete business guides the model; cash-in and cash-out against the bank make reconciliation natural; each capability teaches something different (states, multi-posting entries, policies, close) | General accounting for one company (little concurrency); a generic ledger with no business |
| 23 | **Chart of accounts**: 5 account classes (asset, liability, equity, revenue, expense) with debit or credit normal balance. System accounts per tenant: customer wallets (liability), bank settlement (asset, reconciled against the statement), fee revenue (revenue) and suspense for discrepancies | Just enough for the balance sheet to balance and balances to carry the right sign | The Colombian PUC (structure that teaches nothing about Spring); flat accounts without class |
| 24 | **Bounded contexts**: Ledger (core), Approvals and Audit (supporting, `ledger-app` modules), Reconciliation (supporting; module in phase 1, service in phase 2), Webhooks (supporting, `webhooks` service) and Identity & Access (generic, `auth-server`). The BFF is an adapter, not a context | Each context has its own language and owns its data; Modulith modules are the boundary in code | A single "ledger" context with everything inside |
| 25 | **Context map**: Ledger is upstream with an Open Host Service (REST API, including the journal by sequence) and a Published Language (versioned integration events); Reconciliation is its customer. The bank enters Reconciliation through an anti-corruption layer (CSV → `StatementLine`). Webhooks consumes the same Published Language. A discrepancy produces an adjustment proposal that Approvals puts through dual approval before the Ledger posts it. All are Conformist to Identity (OAuth2/OIDC as is) | Explicit relationships say who adapts to whom and where translation happens | Reconciliation reading the ledger's tables |
| 26 | **Ledger aggregates**: `Account` (class, normal balance, policy; book, held and available balances), `Transfer` (`PENDING` → `POSTED` / `VOIDED` / `EXPIRED`), `JournalEntry` (immutable, ≥2 balancing postings, booking date, value date, `reversalOf`), `BusinessDay` (`OPEN` / `CLOSED`, immutable closing balances), `FeeSchedule` and `AccountPolicy` (changed through dual approval). **Explicit exception**: posting a transfer modifies `Transfer`, two or three `Account`s and creates a `JournalEntry` in one transaction | The "one aggregate per transaction" rule yields to the atomicity of money (decision 5) | A saga across aggregates to move money |
| 27 | **Multi-tenant**: each fintech is a tenant; every row carries `tenant_id` and Postgres enforces RLS. The app sets the tenant per transaction with `SET LOCAL`, its role has no `BYPASSRLS`, and migrations run with a different role | A query that forgets the filter does not expose another fintech's data: the defense lives in the database, like decision 10 | `tenant_id` filtered only in the app; a schema per tenant (migrations × N) |
| 28 | **Persistence**: writes with JPA (Hibernate), with JPA entities separate from the domain and mapped in the adapter; reads with `JdbcClient` and SQL returning DTOs through dedicated query ports (light CQRS, same database and same consistency); Flyway | The domain does not depend on JPA; reads do not load aggregates to render tables | Domain aggregates annotated with JPA; an asynchronous read model in the ledger (balances must be consistent immediately) |
| 29 | **Concurrency**: `READ COMMITTED` with explicit locks. Wallets: balance stored in the row, `SELECT … FOR UPDATE` ordered by id, and `@Version` for policy changes. System accounts (fees, settlement, suspense): no lock and no stored balance; they only receive postings, and their balance is the previous day's closing balance plus the sum of the day's postings | System accounts do not validate balance, so locking them would only serialize every transfer of the tenant; the daily close keeps the sum cheap | `SERIALIZABLE` (retry storms); locking every account; balance split across N rows (complexity with no volume to justify it) |
| 30 | **Idempotency**: a table keyed by tenant, client and `Idempotency-Key`, with the body hash and the stored response, inserted in the same transaction as the operation. The same key while in progress returns 409; with a different body, 422; the original response is replayed for 24 h | A network retry never moves money twice | Idempotency in a cache outside the transaction |
| 31 | **Amounts and identifiers**: amounts in minor units (`bigint`) + `currency char(3)`; `Money` converts with its currency's scale and rounds fees with `HALF_EVEN`. UUIDv7 IDs generated in the domain through a port | Minor units work for any currency without schema changes; UUIDv7 is index-friendly | `numeric(19,2)` (fixes 2 decimals); auto-increment IDs (leak volume and collide across services) |
| 32 | **Jobs**: daily close with Spring Batch partitioned by tenant (each partition sets its tenant for RLS), launched by the scheduler at 00:00 COT; hold expiry every minute inside the API with ShedLock | The close is a resumable batch; expiry needs minute-level latency, which a per-minute Fargate task does not give | `@Scheduled` without a lock (runs on every instance) |
| 33 | **Audit**: each audit event is inserted in the same transaction as the operation, in a table where the app can only insert. A single sealer (ShedLock) chains them by hash in commit order every minute, and each day's chain head is anchored in S3 with Object Lock in compliance mode (Bucket Lock on GCP) | No hot spot on the last link; the one-minute window is protected by database permissions; the external anchor stops a database admin from rewriting the chain | Hashing in the same transaction (serializes the tenant's writes); a Merkle tree per batch (more complex with no need) |
| 34 | **Event transport**: Modulith outbox → **SNS FIFO topic** → one **SQS FIFO queue per consumer**, each with its DLQ, from phase 1. `MessageGroupId` = `tenantId` (Spring Cloud AWS `spring-cloud-aws-modulith-events-sns` takes it from the key in `@Externalized("ledger-events.fifo::#{tenantId()}")`) and content-based deduplication. Phase 1: one queue (webhooks); in phase 2 reconciliation adds its queue without touching the producer. GCP: a Pub/Sub topic with one subscription per consumer, ordering keys and a dead-letter topic, through its own externalizer; both live in the image and are enabled by configuration. Local: Floci's SNS and SQS FIFO. To rebuild a projection, the journal is re-read from the ledger API (`GET /v1/journal-entries?afterSequence=…`), which already is an ordered, immutable log | Covers what the system needs (per-tenant order, fan-out to several consumers, guaranteed delivery, DLQ, rebuild) with the minimum: no servers to run and plenty of headroom for the volume | Kafka/MSK (the most expensive and complex component, for two consumers and little volume; its replay duplicates the log the journal already is); one shared queue (each message reaches a single consumer); an HTTP feed without a broker (every consumer polls and webhooks lose the managed DLQ) |
| 35 | **Integration events**: domain events do not leave the module; a synchronous listener translates them into `JournalEntryPostedV1` (a record in `api.events`, `@Externalized`), stored in `event_publication` in the same transaction. Modulith marks it completed only when the queue confirms, and resends pending ones on restart. Same for `Transfer` state changes (`TransferStatusChangedV1`) | No entry without an event and no event without an entry; the internal model changes without breaking consumers | Publishing domain events as the contract; publishing to the queue outside the transaction |
| 36 | **Event contract**: JSON with JSON Schema in `contracts/events/`, CloudEvents metadata in the message attributes, version in the name (`ledger.journal-entry.posted.v1`) and a contract test in CI. Each event carries a per-tenant sequence | Consumers detect gaps and reordering; a breaking contract change does not compile | Schema registry (no teams to justify it) |
| 37 | **Consumers**: idempotent (the processed `eventId` is stored in the same transaction as its effect), retries through visibility timeout with `maxReceiveCount`, and a DLQ with reprocessing from the console | At-least-once delivery without duplicate effects | Relying on queue deduplication (it lasts only 5 minutes and does not cover the database effect) |
| 38 | **Webhooks**: its own `webhooks` service from phase 1, consuming the queue. Fintechs register their endpoint from the developer portal. Each delivery is signed with JWS (the ledger's key published in its JWKS), retried with exponential backoff (queue visibility timeout) and sent to its queue's DLQ when exhausted. `https` only; private and metadata IPs are rejected (SSRF), and egress uses fixed IPs (NAT) the fintech can allowlist | Outbound HTTP to slow third parties stays isolated from the ledger; this is how any payments API notifies | Status polling; webhooks inside the ledger; HMAC signatures with a shared secret |
| 39 | **Spec-first contract**: `contracts/openapi/ledger-v1.yaml` is the source; openapi-generator produces the Spring interfaces the controllers implement and the console's TypeScript client | A contract change is a YAML diff reviewed before the code; server and console cannot drift | Code-first with springdoc (the contract changes as a side effect) |
| 40 | **Versioning** with Spring Framework 7's native support (`ApiVersionConfigurer.usePathSegment`), version in the path (`/v1`) | Visible in logs, the WAF and CloudFront; no custom versioning code | Version in a header or media type (invisible at the edge) |
| 41 | **API shape**: `ProblemDetail` errors (RFC 9457) with a catalog of stable types (`…/problems/insufficient-funds`); cursor (keyset) pagination; amounts as decimal strings + currency (`{"amount": "150000.00", "currency": "COP"}`) validated against the currency's scale; transfers as resources (`POST /v1/transfers`, `POST /v1/transfers/{id}/post`, `POST /v1/transfers/{id}/void`, `201` with `Location`) | Errors clients can program against; pagination that does not degrade with millions of entries; readable amounts without floats | Offset pagination; amounts as JSON numbers (float); verbs in URLs beyond state transitions |
| 42 | **Per-client rate limit** in the app with Bucket4j on Postgres, on top of the per-IP limit in the WAF | In a multi-tenant API one fintech cannot starve the others; Postgres already exists, so Redis is not needed | Per-IP limit only (a fintech behind few IPs exhausts everyone); Redis just for this |
| 43 | **Identities**: tenant users (finance operator, approver, developer), whose token carries `tenant_id` and sets RLS; platform administrators, global, who cannot see a tenant's data except through break-glass: dual approval, temporary access and an audit record | The settlement account is the fintech's bank account, so its own team reconciles it; platform staff do not need to see tenant data day to day | Platform operators reconciling for every tenant |
| 44 | **Authorization**: scopes for API clients (`transfers:write`, `accounts:read`, …), roles for humans, `@PreAuthorize` on every use case; the approver is never the requester, enforced in the domain and by a database constraint | The dual-approval rule does not depend on the UI honoring it | Authorization only in the UI or the BFF |
| 45 | **Account recovery**: if someone loses their passkey, an admin of their tenant resets it with dual approval | It does not open a path weaker than MFA | Email recovery |
| 46 | **BFF session**: 15 minutes idle, 8 hours maximum, user-initiated logout; if the API returns 401 (revoked token), the BFF ends the session | Revocation reaches the console on the next request | Back-channel logout (Spring Authorization Server does not implement it: [spring-security#18296](https://github.com/spring-projects/spring-security/issues/18296)) |
| 47 | **Keys**: the auth-server signing key, the BFF's DPoP and `private_key_jwt` keys and the webhooks JWS key live in Secrets Manager (encrypted with KMS); rotation with two active keys published in the JWKS | Rotate without cutting anyone off; keys never live in the image or the repo | Signing every token inside KMS (latency and an SDK on the critical path, with no need at this volume) |

Rules: every cloud meets the full contract (WAF, customer-managed keys, official Terraform
provider); only standard Postgres with Flyway; one Terraform module per provider with the same
outputs; no cloud SDK outside an adapter. The same image runs on AWS and GCP; the event
externalizer is chosen by configuration.

Verification checklist: **OWASP ASVS level 3**. Spring Authorization Server lives inside Spring
Security 7.0.

**Verification of decision 8 (opaque + DPoP)** — checked in the Spring Security source (released
since 7.0.0, current in 7.1.1 and on `main`):

1. The token endpoint extracts the DPoP proof in the authorization_code, client_credentials and
   refresh_token grants (`OAuth2EndpointUtils`).
2. `OAuth2AccessTokenGenerator`, which generates opaque tokens, passes the proof to the default
   customizer, and `DefaultOAuth2TokenCustomizers` adds `cnf.jkt`. That customizer always applies,
   even when we register our own (`OAuth2ConfigurerUtils.getAccessTokenCustomizer`).
3. With `cnf.jkt` present, the token is issued as `token_type=DPoP`
   (`OAuth2AuthenticationProviderUtils`).
4. Introspection returns the token's stored claims, including `cnf`
   (`OAuth2TokenIntrospectionAuthenticationProvider`).
5. In the ledger, `SpringOpaqueTokenIntrospector` keeps every claim, and
   `DPoPAuthenticationProvider` validates the proof against the token attributes regardless of
   format: `oauth2ResourceServer().opaqueToken().dPoP()`.

Acceptance criterion: an integration test proves that an opaque token used without its DPoP proof,
or with the wrong key, gets 401.

## Definition of done

Each criterion is an automated test in CI or a demonstrable live check.

**Phase 0 (plain Java)**
- `Money` respects each currency's scale.
- `JournalEntry` rejects an entry that does not balance in some currency.
- The `Transfer` state machine rejects invalid transitions.

**Phase 1: money**
- 100 concurrent transfers on the same wallet: no negative balance and everything balances. System
  accounts do not serialize, measured against a baseline that locks every account.
- The same `Idempotency-Key` returns the same response without duplicating money; with a different
  body, 422.
- A hold lowers the available balance but not the book balance; it expires on its own and voiding it
  releases it.
- A transfer with a fee produces a balanced three-posting journal entry.
- Nothing posts on a closed day; closing balances match the sum of postings.
- Enabling USD in a test is configuration only.

**Phase 1: security**
- Opaque token without a DPoP proof, with the wrong key or sent as Bearer: 401.
- Transfer above the threshold without a passkey: 401 with `insufficient_user_authentication`.
- A tenant A query without a filter sees no tenant B rows (RLS).
- An `UPDATE` on journal entries fails in the database.
- A tampered audit chain is detected against the S3 anchor.
- The approver cannot be the requester.
- A break-glass access shows up in the audit log.
- A webhook to a private IP is rejected; its signature verifies against the published JWKS.
- STRIDE written and ASVS level 3 checklist signed off item by item.

**Phase 1: events, batch and platform**
- The app dies after the commit: the event goes out on restart. A duplicate has no effect. A poison
  message ends in the DLQ and is reprocessed from the console.
- The daily close or reconciliation dies halfway: they resume without duplicating.
- `terraform apply` against Floci brings everything up locally.
- The same signed image runs on AWS and GCP.
- PITR restore tested.
- `terraform destroy` leaves zero resources.
